# Course Catalog DaaS

A small **Data as a Service (DaaS)** application. A SQLite database of university courses is exposed to clients through a read-only REST API, built with Flask and deployed on Render.

Built for **CSE540 Cloud Computing, Lab Experiment 7: Development and Deployment of Data as a Service (DaaS)**, Ahmedabad University.

**Live service:** https://daas-lab7a.onrender.com

Try it: [`/health`](https://daas-lab7a.onrender.com/health) · [`/api/courses?q=cloud`](https://daas-lab7a.onrender.com/api/courses?q=cloud) · [`/api/departments`](https://daas-lab7a.onrender.com/api/departments) · [`/api/stats`](https://daas-lab7a.onrender.com/api/stats)

> The service runs on Render's free plan, which spins down after a period of inactivity. The first request after an idle period can take 50 seconds or more. Later requests are fast.

## Features

- Retrieve a single course by its code.
- Search courses by keyword and filter by department, level, semester, instructor, credits and seat availability.
- Sort and paginate results.
- Summary endpoints for departments and overall statistics.
- Read-only: the database is opened in read-only mode and only `GET` is accepted.
- Safe queries: all SQL is parameterised and the sort column is checked against an allowed list.
- Clear JSON errors: `400` for a bad parameter, `404` for an unknown course, `405` for a wrong method.
- A `X-Response-Time-ms` header on every response.

## Architecture

```
 Clients                     Render                    Service                     Data
┌────────────┐  HTTPS   ┌───────────────┐  WSGI   ┌──────────────────┐  SQL   ┌──────────────┐
│ Browser    │ ───────► │ Web service   │ ──────► │ gunicorn (2      │ ─────► │ SQLite       │
│ curl       │          │ (free plan)   │         │ workers) + Flask │        │ courses.db   │
│ Python app │ ◄─────── │               │ ◄────── │ app.py           │ ◄───── │ (read-only)  │
└────────────┘   JSON   └───────────────┘         └──────────────────┘        └──────────────┘
```

| Layer | Component | Role |
|---|---|---|
| Client | Browser, curl, `test_clients.py` | Send HTTP GET requests |
| Platform | Render web service | Builds the project from GitHub, provides HTTPS and a public URL |
| Service | Flask app run by gunicorn | Validates parameters, runs parameterised SQL, returns JSON |
| Data | SQLite file `courses.db` | Stores the course records |

The database is created during the build step (`python seed_db.py`), so the deployed service is self-contained. This is needed because Render's free plan does not keep files between deploys.

## Dataset

One table, `courses`, with **30 synthetic course records** across five departments (CSE, MGT, MAT, ECE, HSS). The data is generated by `seed_db.py` with a fixed random seed, so it is identical on every build.

| Column | Type | Description |
|---|---|---|
| `code` (primary key) | TEXT | Course code, for example `CSE168` |
| `title` | TEXT | Course title |
| `department` | TEXT | CSE, MGT, MAT, ECE or HSS |
| `level` | INTEGER | 100 to 500 |
| `credits` | INTEGER | 2, 3 or 4 |
| `semester` | TEXT | Monsoon, Winter or Summer |
| `instructor` | TEXT | Instructor name |
| `capacity` | INTEGER | Seat capacity |
| `enrolled` | INTEGER | Students enrolled |
| `description` | TEXT | Short course description |

Indexes exist on `department`, `level` and `semester`.

## API reference

Base URL: `https://daas-lab7a.onrender.com` (or `http://127.0.0.1:5000` when running locally). All endpoints use `GET` and return JSON.

| Endpoint | Description |
|---|---|
| `/` | Service name, version and list of endpoints |
| `/health` | Liveness check and number of courses |
| `/api/courses` | List and search courses (parameters below) |
| `/api/courses/<code>` | One course by code, case-insensitive |
| `/api/departments` | Course count and average credits per department |
| `/api/stats` | Totals, plus counts by semester and by level |

### `GET /api/courses` parameters

| Parameter | Meaning | Example |
|---|---|---|
| `q` | Keyword searched in title, description and code | `q=cloud` |
| `department` | Exact department code | `department=CSE` |
| `level` | Course level (integer) | `level=300` |
| `semester` | Monsoon, Winter or Summer | `semester=Winter` |
| `instructor` | Part of the instructor name | `instructor=Mehta` |
| `min_credits`, `max_credits` | Credit range (integers) | `min_credits=3` |
| `available` | Only courses with free seats | `available=true` |
| `sort` | Sort field: `code`, `title`, `department`, `level`, `credits`, `semester`, `enrolled`, `capacity` | `sort=title` |
| `order` | `asc` (default) or `desc` | `order=desc` |
| `limit` | Page size, default 20, maximum 100 | `limit=5` |
| `offset` | Number of records to skip | `offset=10` |

### Example requests

```bash
# Health check
curl https://daas-lab7a.onrender.com/health
# {"status": "ok", "courses": 30}

# Keyword search
curl "https://daas-lab7a.onrender.com/api/courses?q=cloud"

# CSE courses at level 300, sorted by title
curl "https://daas-lab7a.onrender.com/api/courses?department=CSE&level=300&sort=title"

# Courses with free seats, first 5
curl "https://daas-lab7a.onrender.com/api/courses?available=true&limit=5"

# One course
curl https://daas-lab7a.onrender.com/api/courses/CSE168

# Summaries
curl https://daas-lab7a.onrender.com/api/departments
curl https://daas-lab7a.onrender.com/api/stats
```

### Errors

| Status | When | Example |
|---|---|---|
| `400` | A parameter has an invalid value | `/api/courses?level=abc` |
| `404` | Unknown course code or path | `/api/courses/XXX000` |
| `405` | Any method other than GET | `POST /api/courses` |
| `503` | The database cannot be opened | `/health` |

Errors look like `{"error": "course 'XXX000' not found"}`.

## Run it locally

You need Python 3.10 or newer.

**Windows (PowerShell)**

```powershell
git clone https://github.com/shifaa174/daas-lab7A.git
cd daas-lab7A
py -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python seed_db.py
python app.py
```

**macOS / Linux**

```bash
git clone https://github.com/shifaa174/daas-lab7A.git
cd daas-lab7A
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python seed_db.py
python app.py
```

`seed_db.py` prints `Created courses.db with 30 courses`. The server then runs at http://127.0.0.1:5000. To run it the way production does, use `gunicorn app:app` instead of `python app.py` (gunicorn works on macOS and Linux, not natively on Windows).

## Deploy

### Render (used for the live service)

1. Push this repository to GitHub.
2. On [render.com](https://render.com), choose **New → Web Service** and select the repository.
3. Use these settings (they are also in `render.yaml`):

   | Setting | Value |
   |---|---|
   | Runtime | Python |
   | Build command | `pip install -r requirements.txt && python seed_db.py` |
   | Start command | `gunicorn --bind 0.0.0.0:$PORT --workers 2 app:app` |
   | Health check path | `/health` |
   | Plan | Free |

4. Deploy. When the log says the service is live, open `<your-url>/health`.

Render redeploys automatically on every push to the main branch.

### Docker

```bash
docker build -t course-daas .
docker run -p 8000:8000 course-daas
# open http://127.0.0.1:8000/health
```

The image installs the dependencies, builds the database and starts gunicorn.

### Other platforms

The `Procfile` (`web: python seed_db.py && gunicorn --bind 0.0.0.0:$PORT --workers 2 app:app`) works on Procfile-based platforms such as Railway or Heroku.

## Test with multiple clients

`test_clients.py` simulates several clients at once. Each client sends 10 different requests per round, including one deliberately invalid request (expects 400) and one unknown course (expects 404), and the script checks every status code.

```bash
python test_clients.py https://daas-lab7a.onrender.com --clients 10 --rounds 5
```

Options: `--clients` (default 5) and `--rounds` (default 3). The script prints throughput, latency statistics, a per-request summary and ends with `RESULT: PASS` or `RESULT: FAIL`.

### Observations

- **Correctness.** All 500 requests from 10 concurrent clients returned the expected status code, including the invalid request (400) and the unknown course (404). Retrieval, search, filtering and summaries all worked on the deployed service.
- **Latency.** Most requests took about 285 to 310 ms, with a 95th percentile of 364.7 ms. The endpoints had almost the same latency, so the time was mostly network and platform overhead, not the database query. SQLite answers queries on a 30-row table very quickly.
- **First-request overhead.** The health check averaged 675.8 ms and the maximum latency was 2539.7 ms. The health check is the first request each client sends, so this is probably the cost of the first HTTPS connection, which later requests on the same connection avoid.
- **Throughput.** The service handled 28.4 requests per second with two workers on the free plan. This is enough for the lab but is limited by the small instance and the network distance.
- **Cold start.** Render warns that a free instance spins down after inactivity and the next request can be delayed by 50 seconds or more.
- **Deployment.** The project is plain Flask with a requirements file, so the deploy was simple. The database is built during the build step because the free plan does not keep files between deploys.
- **Why DaaS.** Clients only need the URL and the API description. They need no database driver, no schema knowledge and no local copy of the data, and many different clients can use the same service at once.

### Conclusion

A Data as a Service application was built with a SQLite database and a Flask REST API that supports record retrieval, search, filtering and summaries. It was deployed on Render and verified from a browser and from 10 concurrent clients sending 500 requests, all of which received the expected responses. On a free plan the response time depends mainly on the network and cold starts rather than on the database.

## Limitations and future work

- SQLite is a single-file database and suits only a small, read-mostly dataset. A production service would use a managed database such as PostgreSQL.
- There is no authentication or rate limiting. API keys and rate limits would be the next step.
- The data is static and synthetic. A real version would load a real dataset and provide a way to update it.
- Responses are not cached. Caching would reduce load and latency for repeated queries.
- The free Render plan has cold starts. A paid always-on instance would remove the delay.
